# 主流框架的选型与对比

* 第一代智能体框架：LangChain 和 LlamaIndex
* 新一代智能体框架：是多智能体协作 (Multi-Agent Collaboration) 和 复杂工作流控制 (Complex Workflow Control)。

# AutoGen（群聊）

## 架构

![分词](..\..\docs\images\6-figures\02.png)

* 核心思想是通过对话实现协作
* 它将多智能体系统抽象为一个由多个“可对话”智能体组成的群聊

## 局限

* 虽然 RoundRobinGroupChat 提供了顺序化的流程，但基于 LLM 的对话本质上具有不确定性。智能体可能会
  产生偏离预期的回复，导致对话走向意外的分支，甚至陷入循环
* 当智能体团队的工作结果未达预期时，调试过程可能非常棘手。与传统程序不同，我们得到的不是清晰的错误堆栈，而是一长串的对话历史。这被称为“对话式调试”的难题。

# AgentScope（工程化）

## 架构

![分词](..\..\docs\images\6-figures\03.png)

* 工程化优先的多智能体平台，易用性和工程化（开发+测试+部署全生命周期）
* 它不仅提供了直观易用的编程接口，更重要的是内置了分布式部署、容错恢复、可观测性（Studio）等企业级特性，使其特别适合构建需要长期稳定运行的生产环境应用。
* 组合式架构
    * 多智能体协作层
        * MsgHub 消息中心，负责智能体间的消息路由和状态管理
        * Pipeline 工作流编码，支持顺序、并发等多种执行模式
    * 智能体基础设施层
        * 使用浏览器智能体
        * 深度研究智能体
        * 推理执行智能体
        * 钩子
        * 并行执行
    * 基础设施层
        * Message
        * Memory
* 消息驱动
    * 异步解耦: 消息的发送方和接收方在时间上解耦，无需相互等待，天然支持高并发场景
    * 位置透明: 智能体无需关心另一个智能体是在本地进程还是在远程服务器上，消息系统会自动处理路由
    * 可观测性: 每一条消息都可以被记录、追踪和分析，极大地简化了复杂系统的调试与监控
    * 可靠性: 消息可以被持久化存储和重试，即使系统出现故障，也能保证交互的最终一致性，提升了系统的容错能力

## 局限性

* 对于简单智能体对话，这种架构显得复杂，AgentScope更适合需要构建大规模、高可靠性的生产级多智能体系统
* 对于快速原型开发或简单应用场景，选择更轻量级的框架可能更为合适

# CAMEL

## 架构

* 核心理念是，我们只需要为两个智能体（例如，AI研究员 和 Python程序员）设定好各自的角色和共同的任务目标，它们就能在“初始提示 (
  Inception Prompting)”的引导下，自主地进行多轮对话，相互启发、相互配合，共同完成任务。它极大地降低了设计多智能体对话流程的复杂度

* 角色扮演 (Role-Playing) 的协作方法
    * 一个扮演“AI 用户” (AI User)，负责提出需求、下达指令和构思任务步骤
    * 另一个则扮演“AI 助理” (AI Assistant)，负责根据指令执行具体操作和提供解决方案

* 引导性提示 (Inception Prompting)：如何确保两个 AI 在没有人类持续监督的情况下，能始终“待在自己的角色里”，并且高效地朝着共同目标前进呢？
    * 明确自身角色：例如，“你是一位资深的股票交易员...”
    * 告知协作者角色：例如，“你正在与一位优秀的 Python 程序员合作...”
    * 定义共同目标：例如，“你们的共同目标是开发一个股票交易策略分析工具。”
    * 设定行为约束和沟通协议：这是最关键的一环。例如，指令会要求 AI 用户“一次只提出一个清晰、具体的步骤”，并要求 AI
      助理“在完成上一步之前不要追问更多细节”，同时规定双方需在回复的末尾使用特定标志（如<SOLUTION> ）来标识任务的完成。
      ![分词](..\..\docs\images\6-figures\04.png)

## 局限性

* 提示工程高度依赖
    * 优势：轻架构，重提示。相应的局限性是对提示工程的高度依赖。
    * 提示设计门槛：需要深入理解目标领域和 LLM 的行为特性
    * 调试复杂性：当协作效果不佳时，很难定位是角色定义、任务描述还是交互规则的问题
    * 一致性挑战：不同的 LLM 对相同提示的理解可能存在差异
* 协作规模限制
    * 对话管理：缺乏像 AutoGen 那样的复杂对话路由机制
    * 状态同步：没有 AgentScope 那样的分布式状态管理能力
    * 冲突解决：当多个智能体意见分歧时，缺乏有效的仲裁机制
* CAMEL 特别适合需要深度协作和创造性思维的任务，但在某些场景下可能不是最优选择
    * 【严格流程控制】：对于需要精确步骤控制的任务，LangGraph 的图结构更合适
    * 【大规模并发】：AgentScope 的消息驱动架构在高并发场景下更有优势
    * 【复杂决策树】：AutoGen 的群聊模式在多方决策场景下更加灵活

# LangGraph（状态机/工作流）

## 架构

* 作为 LangChain 生态的扩展，LangGraph 将智能体的执行流程建模为一种状态机（State Machine），并将其表示为有向图（Directed
  Graph），图的节点（Nodes）代表一个具体的计算步骤（如调用LLM、执行工具），而边（Edges）则定义了从一个节点到另一个节点的跳转逻辑

* 三个基本构成要素
    * 全局状态
        * 整个图的执行过程都围绕一个共享的状态对象进行（用于节点交互）
        * 这个状态通常被定义为一个Python 的 TypedDict ，它可以包含任何你需要追踪的信息，如对话历史、中间结果、迭代次数等
    * 节点（Nodes），节点是执行具体工作的单元。每个节点都是一个接收【当前状态】作为输入、并返回一个【更新后的状态】作为输出的Python函数
    * 边（Edges）。边负责连接节点，定义工作流的方向
        * 最简单的边是常规边，它指定了一个节点的输出总是流向另一个固定的节点
        * LangGraph 最强大的功能在于条件边（Conditional Edges）。它通过一个函数来判断当前的状态，然后动态地决定下一步应该跳转到哪个节点。这正是实现循环和复杂逻辑分支的关键

## 优势

* 高度的可控性与可预测性
* 最强大的特性在于对循环（Cycles）的原生支持。通过【条件边】，我们可以轻松构建“反思-修正”循环
* 每个节点都是一个独立的 Python 函数，这带来了高度的模块化
* 在流程中插入一个等待人类审核的节点也变得非常直接，为实现可靠的“人机协作”（Human-in-the-loop）提供了坚实的基础

## 局限性

* LangGraph 需要开发者编写更多的前期代码（Boilerplate），比如定义节点，边等
* 开发者需要更多地思考“如何控制流程（how）”，而不仅仅是“做什么（what）
* 调试过程同样存在挑战。虽然流程比对话历史更清晰，但问题可能出在多个环节：某个节点内部的逻辑错误、在节点间传递的状态数据发生异变，或是边跳转的条件判断失误。这要求开发者对整个图的运行机制有全局性的理解
